# Zotero Reader Local AI

@/home/felipebocajr/.codex/RTK.md

- Target Zotero 10.0.x. Use TypeScript bundled into a bootstrapped XPI; isolate internal PDF APIs in the paper adapter.
- Zotero requires a nonempty HTTPS `applications.zotero.update_url`. This personal prototype points at loopback and is updated manually; never add an external update service. Validate activation of every XPI through AddonManager, not just ZIP inspection.
- Reading assistance belongs in popups near the selection. Offer `Explicar trecho` and `Fazer pergunta`; never introduce a sidebar.
- Preserve `selection-popup`, `data-tabstop`, and the textarea's `contenteditable="true"` marker for Zotero's focus/keyboard managers. Handle Enter directly on the textarea and Enter/Space directly on answer-save buttons; validate editing and shortcuts with trusted Gecko keyboard events.
- Send every extractable page of the current PDF. Do not summarize, retrieve subsets, truncate, or silently discard context. Count the actual chat template with the runtime tokenizer and reserve generation space.
- For the pinned LFM runtime, tokenize the rendered template with `add_special:true` and `parse_special:true` to include BOS. Verify preflight counts against `timings.prompt_n` and test the exact context boundary.
- Initial questions are independent. Follow-ups retain only the current popup conversation. Never send or display reasoning, persist conversation history automatically, or create annotations as a prerequisite.
- Native preferences offer `responseLanguage`: `pt-BR` (default, including upgrades without this preference) or `en`. Read it per request and reinforce it in the system message and after every user question, beyond the full article/history. Article/question language alone never overrides it; explicit user language requests may. Do not translate stored turns/annotations or restart the server for a language change. Count the reminders in the normal template preflight; keep new evidence separate from the delivered precision baseline.
- Each completed answer offers `Salvar nas anotações`. Persist only that chosen final answer, its question and original selected text as a new native PDF highlight/comment; never overwrite an existing highlight. Snapshot selection coordinates and isolate `Zotero.Annotations.saveFromJSON` in the annotation adapter. Respect read-only/deleted items and prevent duplicate clicks/retries.
- Save state belongs to the specific completed turn, not its array index across resets. Explicit saves may finish after popup close; never update a new conversation or disposed UI. Test native persistence and annotation-tab visibility only in the isolated library.
- Render model answers as Markdown with pinned, locally bundled markdown-it (raw HTML disabled; no remote image or link elements). Use an inline rule before Markdown escaping so pinned KaTeX still renders `\(...\)`, `\[...\]`, `$...$`, `$$...$$` and double-escaped model formulas as safe MathML. Preserve the exact source for history and annotation saving; incomplete/invalid formulas stay readable. Include licenses for bundled dependencies in the XPI.
- Saved AI comments get a separate formatted projection outside Zotero's contenteditable; show the original native editor on focus and never save generated markup. Initialize existing readers and annotation-header events, remove projections/observers on shutdown, and guard by the DOM stylesheet ID because Gecko can expose different wrappers for one document. MutationObserver options must be created in the reader's realm.
- Runtime connections and process launches originate from privileged plugin code; connections are loopback-only. Native preferences offer manual start/stop/restart and optional auto-start (off by default), using the chosen project folder and installed Python 3 without a shell. Runtime/model setup remains separate; offline inference must work after setup.
- Pin runtime and weights in `runtime.lock.json`. Compare F16/Q8_0/Q4_K_M from the same checkpoint; K/V remain f16. Keep placement, context, sampling, and cold-prompt handling identical across precisions.
- Offer `lfm2.5-2.6b` (default) and `lfm2.5-8b-a1b` in native preferences and `--model` in setup/serve. The larger model has 128,000 context tokens; 2.6B has 131,072. Keep the legacy lock `model` as the 2.6B benchmark and pin optional weights in `additionalModels`.
- Saving preferences does not restart an active server. Native start/restart applies selected model, port and context with Q4 and adaptive GPU placement; show when a restart is needed. Verify the selected alias with `/v1/models` before sending the article. Preserve model identity/weights across GPU/CPU fallback; never substitute the smaller model. Validate each new model with actual inference and matching template-token counts, separate from the precision baseline.
- The default usage command is `python3 scripts/serve.py`: CUDA all layers first, on GPU OOM try CUDA auto-fit with CPU sharing, then CPU. Prepare both runtimes with `scripts/setup_runtime.py --backend auto`. Preserve requested context, weights and f16 K/V across fallback; use explicit positive `--ctx-size` and the same `--fit-ctx` floor.
- Explicit `--backend cpu/cuda`, `--gpu-layers` or `--binary` select fixed placement without fallback. The precision benchmark keeps 24 GPU layers for every variant. Never mix adaptive usage measurements with fixed-placement comparisons; include the launcher in the experiment fingerprint.
- The auto supervisor owns and cancels only its child. GPU OOM during a request interrupts it before restarting; do not silently replay questions. Keep transient status in `.runtime/server-<port>.json`, with no prompts or conversation history.
- The plugin owns only Gecko Subprocess handles it created, never PIDs recovered from status files. Detect external servers and never stop/adopt them. Serialize duplicate starts, reap late launches after cancellation, and cancel requests before stop/restart/disable. The UI-managed launcher uses `--managed --parent-pid`: stdin EOF or parent exit reaps its llama child; CLI/experiment modes keep their existing lifecycle.
- Extract runtime archives into staging before publishing files with atomic rename. Never overwrite/truncate a running server's mapped libraries or executable in place.
- Validate with `npm run check`, `npm test`, `npm run test:runtime`, `npm run build`, then the isolated Zotero development profile for plugin changes. Runtime placement changes also require actual inference and VRAM verification. Never test installation or imports in the user's normal profile/library.
- Native validation uses `scripts/setup_dev.py`, a loopback Gecko debugger, and `scripts/rdp.py --file scripts/install_dev.js`. Preference scripts live in a pane sandbox; inline handlers access it through `Zotero_Preferences.getScope()`.
- Preferences sandboxes are destroyed before window unload. Keep async status/process/picker work and unload listeners in the privileged plugin realm, with synchronous pane handlers and polling of snapshots; never await a runtime promise or register an unload callback in the pane. A privileged window-lifetime record cancels pane timers on close/disable; test late replies against a closed native window.
- Store experiment evidence and limitations in `experiments/`, not here. Update this file in the same change when a durable interface or invariant changes.
- Keep the small measured JSONL/CSV/summary/report artifacts versioned. Downloaded papers, weights, runtimes, development profiles and logs stay ignored.
- Canonical GitHub repository: `felipebocajr/zotero-reader-local-ai`, public, default branch `main`. Version source, documentation and small experiment evidence; distribute built XPI files as release assets, keeping `dist/`, `.runtime/`, downloaded papers and local tool metadata out of Git. Preserve manual plugin updates.
- New precision comparisons use a separate `LFM_RESULTS_DIR`; never overwrite the delivered baseline. Record kernel RSS high-water marks as well as request-time samples.
